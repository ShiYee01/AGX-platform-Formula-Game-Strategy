# V2 代码修改理由与验证记录

日期：2026-11-16。基线来自仓库提交 4c24b06，平台记录标为 v1。
本地开发分支：analysis/v2-log-driven。V2 是本次候选代码的名称；平台上传后实际版本号以 AGX 返回值为准。

## 1. 本次改动与对应证据

|模块|旧行为|V2 行为|对应问题与预期|
|---|---|---|---|
|起跑车道|两列从 n=±3.5 立即向 0 合流|先保留发车车道，行进 80 m 后在接下来的 300 m 平滑合流|4 场首圈 damage；降低无必要横移与接触风险|
|横向目标|条件改变时在 0、±2.5 间跳变|目标变化限制为 0.8 m/s，邻车阻挡时保留当前目标|降低换线振荡；不把“意图换线”当作“已经换完”|
|交通限速|主要在前车 12 m 内才减速|按车速、湿度、闭合速度和可用制动预算调整安全距离|更早处理逼近，留出减速距离|
|超车记忆|每次重新选偏移|记录目标车与所选一侧，检查横向通道和未来纵向间隔|减少来回变道；前车已落后才解除目标|
|必要干地换胎|lap>=2 后才提出请求|lap>=1，入口前 200 m 窗口内申请不同干胎|第 3 场进入维修区后仍被 dry_compound_requirement 取消成绩|
|湿地进站|照常执行固定 soft→medium|仅在正赛实际观察到 wet 后记住湿地状态；健康需求仍可进站|避免无条件执行干地计划|
|弯道速度|未来前三点的最紧弯心速度直接压到现在|按全部预览距离传播制动约束，并估计当前曲率|减少重复保守限制，仍保留当前弯与制动预留|
|直线速度|45 m/s 上限|候选 55 m/s 上限|两场 Highland 排位未完成；需要新比赛检验收益与风险|
|姿态异常|直接使用可能超出 ±π 的 heading_error|归一化角度，明显异常时进一步降低目标速度|避免旋转后控制方向不连续|
|boost|直线且有电即可能使用|增加起跑、滑动和横向偏差条件|避免失稳阶段继续额外加速|
|日志拟合|只识别 type=decision|兼容原始字节导出的无 type 决策行，排除进出站跨界样本|修复工具包无法处理本次真实日志的问题|

以上 80/300 m、0.8 m/s、1.5 m 道路边距、2.6/2.8 m 通道判断、55 m/s 上限、200 m 进站窗口和跟车时间参数均为候选控制参数，不是平台官方物理常数或处罚阈值。

## 2. 接口与设计选择

保留 init(context)/act(observation) 和旧版七个动作字段，决策只使用合法当前观测与本人进程记忆。车辆设计书未修改，仍为新版示例的 60 kg 配置。

TRACK_PITS 的三个入口坐标和坐标周期来自仓库公开 data/*.mapdata.json；只嵌入必要的数值，没有引入真实对局的种子、时间表、对手代码或未来天气。通过 observation.track_length_m 匹配赛道，未知赛道不套用另一个入口，而退回不限制窗口的请求方式。

代码仍仅依赖 Python 标准库 math，不需要把地图、NumPy、sim、calibrate、日志或报告放入赛车提交 ZIP。原来的打包器仍可按需打包可选数值地图，本次两文件提交就能运行。

pit_state 非零时仍保持原版的零油门/刹车/转向约定，由平台处理维修区通行。本批数据表明车辆在这些状态下仍会按约 22.22 m/s 通行，不能因策略动作是 0 就误判为卡住；没有擅自改写未知的维修区驾驶机制。

## 3. 已完成验证

### 3.1 初版一致性

逐条重放 199,187 个历史观测，V1 动作与原日志全部匹配，允许 0.000015 的导出小数差异。baselines/v1 的文件由原仓库逐字节备份。

### 3.2 V2 固定观测重放

全部 199,187 个观测均成功返回动作，未出现异常、非有限数、字段缺失、越界、非原生整数模式或错误布尔值；没有同时给正油门和正刹车。历史观测上的横向目标变化率上限为约 0.8 m/s。

本机仅统计候选 act 调用的累计 CPU 约 4.838 秒（11 份日志合计），不包含平台进程、IPC 和机器差异，因此不能作为平台 55 秒限制的正式证明。

第 3 场固定观测中，新版第一次进站请求在相对发车 312.20 s、lap=1、s≈5515.96 m 处；原版首次请求在 318.57 s、lap=2、s≈0.94 m 处，后者已经错过上一圈入口，实际进站直到 476.20 s。请求时间只差约 6 秒，却可能改变是否多等一整圈的入口机会。

第 1、2、6、7、8、11 场的历史观测重放中，V2 不再提出旧版的固定晚进站请求。这是动作差异的事实，不是新比赛中已经减少进站时间的证据。

### 3.3 回归测试

25 项测试通过：20 项车手测试和 5 项日志拟合测试，覆盖起跑保持、缓慢合流、邻车阻挡、提前跟车制动、后车不迫使前车停车、干地提前换胎、湿地记忆、排位与正赛状态隔离、健康进站、维修区动作、完整预览制动、低油量保护及真实日志编码兼容。

日志工具在真实第 1 场导出上产生 25,689 对有效站外观测，确认不再因缺少 type=decision 而丢弃全部样本。输出只是观测运动包络：例如约 44.57 m/s 的速度分位主要反映旧车手上限，不能当作车辆物理极速。拟合结果没有直接注入本轮车手参数；速度预算继续沿用 V1 的基准。

### 3.4 打包与源码核查

正式上传用的 V2 ZIP 根目录只有 agent.py、design.json，二者与仓库当前源文件逐字节相同。已核对 CRC、文件大小、源码语法和 JSON 可解析性；包 SHA-256 与文件清单记录在交付的 submission-manifest.json。

## 4. 验证的边界

固定观测重放不会让新动作反过来改变车辆位置，也不会改变其他车、天气或进站状态。它只能验证输入兼容性和动作逻辑，不能得出“新版会第几名”“提高多少秒”“避免几次碰撞”。本轮未使用官方引擎，也未在 AGX 上传、激活或完成 V2 比赛。

没有把简化质点优化器的结果当成正式比赛成绩，也没有拿这 11 场中已经看过的比赛充当独立留出验证集。

## 5. 需要在下一批真实比赛中检验的假设

|假设|检查方法|回退或调整条件|
|---|---|---|
|提前进站能满足干胎要求|纯干地比赛中核对 pit_exit、完成进站次数、两种配方记录和最终状态|再次 dry_compound_requirement 时优先检查入口机会与实际服务，不只改 lap 阈值|
|起跑保持车道更稳定|统计本人前 40 s 接触事件、0 圈 damage 比例、横向轨迹|若持续早退赛，结合邻车轨迹和合流通道再调整，不能简单继续降速|
|速度规划可改善 Highland 排位|核对 qualifying_lap.valid、末端距离与排位时间|高速越界/滑动增多时，先将 TOP_SPEED 改回 45 做单因素对照|
|湿地取消固定换胎有益|比较同赛道、近似湿度和轮胎条件的圈速、磨损与终局状态|出现轮胎健康问题则调整健康进站触发，不能机械恢复所有湿地固定换胎|

建议先收集 3–5 场检查故障和明显退化；之后争取三条赛道各至少 3 场，并按天气分组。这个数量只用于初步诊断，不构成统计显著性保证。平台若允许同种子、同对手评测，优先进行成对对照；若不能固定条件，就保留种子、赛道、天气和冻结版本，避免单场胜负下结论。

## 6. 本轮文件与复现命令

- agent/agent.py：V2 候选车手。
- agent/design.json：原样车辆设计。
- baselines/v1/：可回退的原始两文件。
- tools/analyze_logs.py：字节完整性、基线重放与观测统计。
- tools/replay_logs.py：V1/V2 固定观测动作检查。
- tests/：回归测试。
- analysis/：派生统计与验证记录，原始日志仍在用户指定的 Formula 文件夹。

```sh
python3 -m unittest discover -s tests -v
python3 tools/analyze_logs.py /Users/syeah/Downloads/Formula --output analysis/baseline-11
python3 tools/replay_logs.py /Users/syeah/Downloads/Formula --output analysis/v2-replay.json
python3 tools/build_submission.py --output submission-v2.zip --manifest submission-v2.manifest.json
```

平台操作仍由用户完成：上传 V2 两文件 ZIP，等待准入，选择接受的版本并更新参赛版本；保存返回的版本 ID，再下载该版本新对局的 training.jsonl 与 public-events.jsonl。
